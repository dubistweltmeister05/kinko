Right, so here's a bit more detailed guide on how to get into OS, and a bit more about the intricacies that you can expect to be challenging to you.

The recommended way from me, is still the Mastering FreeRTOS manual and a simple WeAct Studios STM32F446 Dev board that you can mess around with. The Manual has all that you need when it comes to theory, and the dev board is more than capable enough to help you implement things.

Also, please - USE LLMs TO HELP YOU LEARN BETTER. PLEASE DO. But do NOT use them to substitute the process of thinking.

Now, some intricacies. Let's start with the Tick source. The concept is quite simple, the OS has 0 sense of time. Or Timing. And that's quite important when it comes to scheduling things, which is the whole point of the RTOS. So, there needs to be a stable, consistent source of rhythm, that the RTOS can take as reference and structure its operation around. On ARM chips like the STM32F446, this usually comes down to configuring the SysTick hardware timer to fire a hardware interrupt at a fixed frequency, typically every 1 millisecond. Every single time that timer overflows, the processor pauses whatever code it's running, hands control to the RTOS tick handler, and increments an internal counter. That tick handler is the heart rate of your system. It is where the scheduler checks if a sleeping task needs to wake up, if a timeout has expired, or if it's time to hand the CPU over to a different task. Without that steady heartbeat, the RTOS is completely blind to duration, delay, or cadence.

Next, we have processes, threads, and tasks. When you come from desktop systems like Linux or Windows, you're used to a clear boundary between a process, which has its own isolated memory space via virtual memory, and threads, which share memory within that process. On microcontrollers, you can essentially drop the concept of traditional processes altogether. Small microcontrollers rarely have a full Memory Management Unit to enforce memory isolation, so everything lives in one big, flat physical memory space. In an RTOS context, we talk about tasks. A task is really just a simple, self-contained C function that runs in an infinite loop, never returning. The RTOS creates the illusion of running multiple tasks simultaneously by performing context switches. When it decides to switch tasks, it saves all the CPU registers of the current task onto its stack, updates the stack pointer, loads the saved register state of the next task, and jumps straight into its code. To the hardware, it is just executing instructions continuously, but to you, it looks like a bunch of independent programs executing in parallel.

You need to also take a good long look at their priority, which is a nicer way of saying what needs done ASAP and what can wait and be tackled in the CPU's free-time, so to speak. Priority in a real-time system isn't a friendly suggestion or a general hint to the system, it is a strict operational rule. The FreeRTOS scheduler operates on a strict preemptive basis, meaning the highest-priority task that is ready to run will ALWAYS get the CPU. If a low-priority task is mid-execution and a high-priority task suddenly becomes ready because new sensor data came in, the RTOS immediately suspends the lower one and hands over the core. If multiple tasks share the exact same priority, the RTOS will divide time between them using time-slicing on every tick interrupt. But this strict priority mechanism brings a major trap known as task starvation. If you write a high-priority task that spends all its time processing data in a tight loop without explicitly yielding or blocking to wait for an event, lower-priority tasks will literally never run a single instruction. Designing a stable RTOS application means ensuring high-priority tasks do their job quickly, block themselves to wait for the next event, and get out of the way.

Then, shall come the things that help make comms between them easier and help protect data from corruption - Semaphores, Mutexs, Locks, and Queues. Since every task shares the same memory space, if two tasks try to write to the same buffer or talk to the same hardware peripheral at once, you get instant data corruption. Queues are your primary tool for moving data safely from one place to another; they copy data safely between tasks and handle blocking for you when a queue is empty or full. Semaphores are used for signaling events rather than passing actual payload data, where a hardware interrupt can give a semaphore to signal a worker task to wake up and process something. Mutexes are special locks designed specifically for protecting shared resources like an I2C or UART bus. Unlike simple locks, a proper RTOS Mutex includes built-in protection against Priority Inversion. This nasty phenomenon happens when a low-priority task holds a lock, a high-priority task gets blocked waiting for that lock, and an unrelated medium-priority task kicks in and starves the low-priority task, unintentionally blocking the high-priority task too. The Mutex solves this via priority inheritance, temporarily boosting the low-priority task's priority so it can finish using the resource quickly and give control to the high-priority task.

Then, you might take a look at interrupt management, and how interrupt priority is managed alongside task priority. It is extremely important to realize that hardware interrupt priority, managed directly by the microcontroller's hardware interrupt controller, sits completely above RTOS task priority. An interrupt will ALWAYS interrupt a running task immediately, regardless of how high that task's priority is set. Because of this, you have to keep your Interrupt Service Routines absurdly short and fast. You should never do heavy processing or wait for slow hardware inside an interrupt. Instead, the interrupt should do the bare minimum, hand off the real work to a task using a queue or a semaphore, and exit. Furthermore, you cannot call standard RTOS API functions inside an interrupt handler because doing so can corrupt scheduler states. You have to use dedicated "FromISR" versions of those functions, which safely handle communication from interrupt context and can request the RTOS to perform a context switch immediately as the interrupt exits.

A nice way to put this all together, is memory management, critical sections, what makes them special and how to protect them, how to manage the heap and stack, and a lot more that comes with it. Memory management on a microcontroller requires you to be very explicit about where every byte goes. When you create a task, the RTOS allocates a dedicated slice of RAM to act as that specific task's stack, which holds its local variables, function arguments, and saved CPU state during a context switch. If a task uses too many nested functions or huge local arrays, it will overflow its stack and corrupt adjacent memory, making stack monitoring tools during development non-negotiable. For dynamic allocations, FreeRTOS provides configurable heap management schemes that let you pick the right balance between static allocations, simple dynamic allocation, or full thread-safe memory management. Finally, when you have quick code operations that absolutely cannot be interrupted by anything - like modifying a shared global bit-mask - you wrap them in a critical section. Entering a critical section temporarily disables hardware interrupts up to a configured threshold, ensuring that neither another task nor an interrupt can touch the system mid-operation. Keeping these critical sections down to just a few nanoseconds is the key to maintaining a system that stays truly real-time.
